title: "CI pipeline and a real migration runner"
summary: "Every pull request is now gated by lint, typecheck, tests, a real Docker image build, and a live migration rehearsal — and schema changes are applied by an in-repo runner that keeps a checksummed ledger of what ran where."
new:
  - title: "GitHub Actions CI"
    detail: "Four jobs on every PR: verify (lint, typecheck, all tests, Node-pin agreement, and a guard that no unvalidated request-body cast creeps back in), build (the actual production Dockerfile, asserting the migration runner and SQL made it into the image), guards (migrations are append-only for all authors, and the version-bump + release-notes rule is enforced), and migrations (a MySQL 8.4 service where schema.sql is loaded, baselined through 025, migrated up twice, and re-run to prove idempotency). Known limitation: the migrations job validates against the schema.sql shape, not production's drifted BIGINT signedness — it proves the SQL is valid and idempotent, not that it will run in prod."
  - title: "Migration runner with a ledger"
    detail: "node scripts/migrate.mjs brings up / status / baseline / verify / verify-idempotent. It records every applied migration in a schema_migrations table with a SHA-256 checksum, refuses checksum drift, takes an advisory lock so replicas can't race, and splits the repo's DELIMITER-based idempotent migrations correctly (a unit-tested pure splitter). Deliberately no down command: MySQL cannot roll back DDL — the posture is forward-only plus restore-from-backup, with idempotency enforced in CI. On failure it stops, records nothing, prints the failing statement, and loudly marks the file PARTIALLY APPLIED."
improved:
  - title: "Deploys run migrations automatically"
    detail: "The Docker image now carries migrations/ and the runner, so Coolify's pre-deployment command (node scripts/migrate.mjs up) applies pending migrations once, before containers take traffic — a failure aborts the deploy with the old version still serving. The README deployment section documents the new flow and the one-time baseline (--through 025) each existing database needs. A separate MIGRATION_DATABASE_URL lets the migrating identity hold DDL privileges while the app user stays DML-only."
